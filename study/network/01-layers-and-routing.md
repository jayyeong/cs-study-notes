# 01. 계층과 패킷 전달

> 목표: 외부 서버로 요청할 때 IP·MAC·ARP·스위치·라우터가 각각 어떤 문제를 해결하는지 설명한다.

## 1. 계층을 나누는 이유

웹 요청의 의미를 정하는 HTTP가 케이블의 전기 신호까지 처리한다면 전송 매체가 바뀔 때마다 애플리케이션도 바뀌어야 합니다. 계층은 역할과 인터페이스를 나누어 하위 기술의 변경 영향을 줄입니다. 장애를 조사할 때도 주소 해석, 경로, 연결, 응답을 구분할 수 있습니다.

| OSI 계층 | 역할 | 예시·대응 |
|---|---|---|
| 7 응용 | 애플리케이션 간 메시지의 의미 | HTTP, DNS |
| 6 표현 | 데이터 표현·인코딩·암호화 개념 | 실무에서는 라이브러리·프로토콜에 분산 |
| 5 세션 | 대화의 설정·유지·종료 개념 | 실제 구현의 세션과 일대일 대응하지 않음 |
| 4 전송 | 종단 간 전달과 서비스 구분 | TCP, UDP, 포트 |
| 3 네트워크 | 서로 다른 네트워크 사이 전달 | IP, 라우터 |
| 2 데이터 링크 | 링크에서 프레임 전달 | Ethernet, MAC, L2 스위치 |
| 1 물리 | 신호 전달 | 케이블, 광 신호 |

TCP/IP 4계층은 응용·전송·인터넷·링크로 설명합니다. OSI는 참조 모델이고 실제 프로토콜이 항상 7개 독립 모듈로 구현되는 것은 아닙니다. 특히 TLS를 OSI 한 계층에 억지로 고정하기보다 어떤 기능을 제공하는지 설명하는 편이 정확합니다.

## 2. 캡슐화와 전달 단위

HTTP/1.1 over TCP over IPv4 over Ethernet의 예입니다.

```text
HTTP 메시지
  → TCP 헤더 + 바이트 데이터             : 세그먼트
  → IPv4 헤더 + TCP 세그먼트             : IP 패킷
  → Ethernet 헤더 + IP 패킷 + 트레일러   : 프레임
  → 물리 신호
```

수신자는 반대로 해석합니다. 메시지 하나가 TCP 세그먼트 하나와 대응하는 것은 아닙니다. HTTP/3처럼 다른 전송 프로토콜을 사용하는 경우에는 계층 조합도 달라집니다.

## 3. 주소 세 가지

| 주소 | 해결하는 질문 | 주의점 |
|---|---|---|
| IP | 어느 네트워크의 목적지인가? | 인터페이스에 할당되며 NAT로 변환될 수 있음 |
| MAC | 현재 링크에서 누구에게 프레임을 전달하는가? | 변경·가상화될 수 있으므로 영구 신원으로 보지 않음 |
| 포트 | 어떤 전송 계층 서비스/엔드포인트로 전달하는가? | 프로세스와 반드시 1:1은 아님 |

IP의 계층적 주소 체계는 경로를 네트워크 단위로 묶어 관리하는 데 유리합니다. Ethernet에서는 실제 다음 홉에 전달할 프레임 주소도 필요합니다. 모든 링크 기술이 Ethernet MAC을 사용하는 것은 아닙니다.

## 4. 같은 서브넷과 외부 목적지

예시 PC는 `192.168.10.20/24`, 기본 게이트웨이는 `192.168.10.1`입니다.

- 목적지 `192.168.10.30`: 일반적인 직접 연결 경로에서는 목적지 자신의 MAC을 확인합니다.
- 목적지 `203.0.113.10`: 기본 경로를 사용할 경우 게이트웨이의 MAC을 확인합니다.

입문 단계에서는 IP와 서브넷 마스크의 AND 결과를 비교하면 이해하기 쉽습니다. 실제 호스트는 라우팅 테이블을 조회하며, 더 구체적인 경로나 정책이 있다면 단순한 “외부면 무조건 기본 게이트웨이” 설명보다 우선합니다.

ARP는 같은 링크에서 IPv4 주소에 대응하는 링크 주소를 알아내는 데 사용합니다. 일반적인 요청은 브로드캐스트이고 응답은 요청자에게 전달됩니다. 이미 캐시가 있으면 조회 방송을 반복할 필요가 없습니다. 외부 서버의 MAC을 인터넷 전체에 ARP로 묻지 않습니다. IPv6에서는 ARP 대신 Neighbor Discovery를 사용합니다. [RFC 826](https://www.rfc-editor.org/rfc/rfc826.html)

## 5. 스위치와 라우터

**L2 스위치**는 들어온 프레임의 **출발지 MAC과 입력 포트**를 학습합니다. 전달할 때는 목적지 MAC을 조회합니다. 목적지 위치를 모르는 유니캐스트나 브로드캐스트는 같은 VLAN의 적절한 포트로 플러딩합니다. 입력 포트나 전달이 차단된 포트까지 무조건 전송하는 것은 아닙니다.

**라우터**는 목적지 IP와 라우팅 테이블로 다음 홉 및 출력 인터페이스를 결정합니다. 여러 경로가 맞으면 일반적으로 가장 긴 프리픽스가 일치하는 경로를 선택합니다. 예를 들어 `10.0.0.0/8`과 `10.1.0.0/16` 중 목적지 `10.1.2.3`에는 `/16`이 더 구체적입니다.

```mermaid
flowchart LR
    PC[PC] -->|목적지 MAC: 게이트웨이| SW[L2 스위치]
    SW --> R1[라우터 1]
    R1 -->|새 링크 헤더| R2[다음 홉 라우터]
    R2 --> SERVER[목적지 서버]
```

라우터는 수신 링크 헤더를 제거하고 경로를 결정한 뒤 출력 링크에 맞는 새 프레임을 만듭니다. NAT가 없는 일반 IP 전달에서는 출발지·목적지 IP는 유지되지만 TTL은 감소합니다. IPv4에서는 헤더 체크섬도 갱신됩니다. 따라서 “패킷 전체가 변하지 않는다”는 설명은 틀립니다.

## 6. 직접 풀어보기

1. 위 PC가 `203.0.113.10`으로 보낼 때 첫 프레임의 목적지 MAC과 IP는 각각 누구의 것인가?
2. 스위치가 PC의 위치를 배우기 위해 응답 패킷을 기다려야 하는가?
3. 라우터 1이 목적지 서버와 직접 연결되어 있지 않으면 누구의 MAC을 확인하는가?

<details>
<summary>확인 답안</summary>

1. MAC은 게이트웨이, IP는 최종 서버입니다. 기본 경로를 사용하고 NAT 전이라고 가정합니다.
2. 아닙니다. PC가 보낸 프레임의 출발지 MAC을 보고 학습할 수 있습니다.
3. 선택한 출력 링크의 다음 홉입니다. 모든 라우터가 최종 서버의 MAC을 알아야 하는 것은 아닙니다.

</details>

## 7. 면접 전 확인

- [ ] OSI 계층 이름 없이도 주소별 역할을 설명할 수 있다.
- [ ] 브로드캐스트는 수신 대상, 플러딩은 전달 동작이라는 차이를 설명한다.
- [ ] 같은 VLAN, IPv4, Ethernet, NAT 없음 등의 가정을 말할 수 있다.
