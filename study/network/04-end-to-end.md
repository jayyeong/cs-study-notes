# 04. 전체 흐름과 장애 진단

> 목표: 암기한 개념을 실제 요청 한 건에 연결하고, 관측 결과로 원인을 좁힌다.

## 1. HTTPS 주소를 입력했을 때

아래는 캐시·기존 연결이 없고 HTTP/1.1 또는 HTTP/2, IPv4 Ethernet을 사용하는 단순화한 예입니다.

1. 브라우저가 URL을 해석하고 캐시 등 재사용 가능한 정보를 확인합니다.
2. DNS를 통해 접속 후보 주소를 얻습니다. DNS 질의 자체도 네트워크 전송이 필요합니다.
3. OS가 목적지에 대한 경로와 다음 홉을 결정합니다. 필요하면 ARP로 다음 홉의 MAC을 찾습니다.
4. TCP 연결을 설정합니다. 각 세그먼트는 IP 패킷과 링크 프레임에 실려 전달됩니다.
5. TLS에서 서버 신원을 검증하고 통신 보호에 사용할 키를 준비합니다.
6. HTTP 요청이 전달됩니다. 쿠키는 전송 조건을 만족할 때 첨부됩니다.
7. 웹 서버·프록시·애플리케이션이 요청을 처리하고 필요한 경우 DB 등에 접근합니다.
8. HTTP 응답을 받은 브라우저가 내용을 해석합니다. HTML·CSS·JavaScript 및 추가 리소스 요청이 렌더링에 영향을 줍니다.

DNS 이후에만 ARP가 일어난다는 절대적인 시간 순서는 아닙니다. 원격 DNS 리졸버에 질의할 때부터 다음 홉 전달이 필요하고, 캐시가 있으면 ARP 방송은 생략됩니다. HTTP/3에서는 TCP 단계 대신 QUIC의 연결 설정을 설명합니다.

## 2. 어느 단계가 느린가?

| 관측 | 우선 세울 가설 | 추가로 확인할 증거 |
|---|---|---|
| DNS 조회에 긴 시간 | 리졸버 지연·재시도·위임 문제 | 조회 시간, 반환 주소, TTL |
| TCP 연결이 지연 | 경로·방화벽·서버 수용량 문제 | SYN 재전송, 포트 리슨, RTT |
| TLS만 실패 | 호스트명·인증서·프로토콜 협상 문제 | 인증서 오류와 핸드셰이크 로그 |
| 연결 후 첫 바이트가 늦음 | 서버 처리·프록시·DB 대기 | 요청 추적, 처리 시간, 큐 대기 |
| 다운로드만 느림 | 전송량·손실·대역폭 제한 | 응답 크기, 처리량, 재전송 |
| 응답은 빠른데 화면이 늦음 | 렌더링·JS·추가 리소스 | 브라우저 성능 기록 |

한 지표가 원인을 확정하지는 않습니다. 예를 들어 TTFB에는 서버 처리만이 아니라 네트워크 왕복과 중간 장치 영향도 포함될 수 있습니다.

## 3. 상황형 문제와 답변의 방향

### A. ping은 성공하는데 HTTPS 접속은 실패한다

ping은 ICMP 도달성의 일부만 보여줍니다. TCP 443이 열렸는지, TLS 검증에 실패했는지, HTTP 오류인지 단계적으로 확인합니다. ICMP가 막혀도 HTTPS는 정상일 수 있으므로 반대 방향도 성립하지 않습니다.

### B. IP로 접속하면 되는데 도메인으로는 실패한다

DNS 해석 결과와 주소를 비교하되, IP 직접 접속은 Host·SNI·인증서 검증 조건이 달라질 수 있음을 먼저 밝힙니다. “IP로 되니까 DNS 문제 확정”이라고 결론 내리지 않습니다.

### C. 로그인 직후 일부 요청에서 로그아웃된다

요청이 다른 서버로 갈 때 세션 상태를 공유하지 못하는지, 쿠키의 Domain·Path·SameSite·Secure·만료 조건이 맞는지 확인합니다. 증거는 요청별 쿠키 첨부 여부와 처리 서버, 세션 조회 결과입니다. 세션 값을 로그에 그대로 남기지는 않습니다.

### D. 주문 POST가 타임아웃되어 재시도했다

응답을 받지 못했다고 서버가 처리하지 않았다고 단정할 수 없습니다. TCP 재전송과 애플리케이션 재요청도 별개입니다. 주문 식별자·멱등성 키·서버 측 중복 처리 방지를 설계하고 처리 결과를 조회하는 접근을 설명합니다.

### E. 대용량 전송이 느리고 수신 윈도가 거의 0이다

수신 애플리케이션의 읽기 속도와 버퍼 압력을 조사합니다. 단순히 대역폭을 늘리거나 송신량을 높여 해결하려고 하지 않습니다. 반대로 rwnd가 충분해도 혼잡 윈도와 손실 때문에 처리량이 제한될 수 있습니다.

## 4. 안전한 관찰 실습

본인 PC에서 공개 테스트 도메인 `example.com`에 대한 일반 조회만 수행합니다. 실행 결과는 환경에 따라 달라지며, 아래 명령을 이 자료 작성 과정에서 실행해 검증한 것은 아닙니다.

Windows PowerShell:

```powershell
Resolve-DnsName example.com
Test-NetConnection example.com -Port 443
curl.exe -I https://example.com
```

macOS/Linux:

```sh
nslookup example.com
curl -I https://example.com
```

각 결과가 DNS·TCP·HTTP 중 어느 계층을 관측하는지 적습니다. `curl -I`는 HEAD 요청이며 브라우저의 실제 전체 페이지 로딩을 재현하지는 않습니다. 명령 실패는 사이트 장애 외에도 로컬 프록시·방화벽·도구 설치 상태 때문일 수 있습니다.

## 5. 2분 종합 설명 연습

아래 단어를 모두 사용해 한 요청을 설명합니다.

`DNS 캐시 → 리졸버 → 경로 조회 → 다음 홉 → ARP → TCP → TLS → HTTP → Cookie/Session → 응답`

좋은 답변은 시작할 때 버전과 가정을 말하고, 각 단계가 해결하는 문제를 연결합니다. 이름만 나열한 경우 [01](01-layers-and-routing.md)~[03](03-web.md)으로 돌아가 이유를 복습합니다.
